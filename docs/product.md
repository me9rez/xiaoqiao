# 产品文档：小巧（Xiaoqiao）——从 Coding Agent 到自托管个人 Agent

> 状态：草案 v0.1 · 2026-10 · 本文是产品方向的主文档，工程落地方案见 [pivot-plan.md](pivot-plan.md)。
> 产品名：**小巧**（拉丁写法 Xiaoqiao）。发行名 `xiaoqiao`、CLI `xiaoqiao`；`coding-agent` 与旧配置目录 `~/.coding-agent/` 作为兼容别名保留，见 §9 D7。
> 适用范围：仓库 `me9rez/xiaoqiao`。文中「现状」均以 master 分支代码为准；工程计划见 [pivot-plan.md](pivot-plan.md)（v2，基线 `f44ff33`）。

---

## 1. 一句话定位

**住在你自己机器上的个人 Agent：有固定人格、记得你、按点主动干活、能直接操作你的文件和电脑。**

不是「更聪明的聊天框」，也不是「IDE 插件」。它更像一个你雇佣的助理：有名字、有性格、有作息、有自己的工作目录，你没空的时候它也在干活。

---

## 2. 为什么转向

现在的 Coding Agent 是一个**优秀的编码助手**：MAF 驱动的 agent loop、逐 token 事件流、原生 HITL 审批、18 个工具、Skills/MCP、完整的 Web UI。这些是资产，不推倒。

但它有三个天花板：

1. **场景天花板**：只服务「写代码」这一刻。用户一天里 90% 需要被代劳的事不在编辑器里。
2. **形态天花板**：必须打开浏览器、连上 WebSocket 才有 agent。关掉页面，agent 就死了。
3. **产品天花板**：人格、记忆、定时、渠道四个「助理感」的来源，目前**全是装饰**（见 §6）。

转向不是加功能，是换地基：**从一个「会话式工具」变成一台「常驻的、可被多个入口唤起的执行引擎」**。

---

## 3. 目标用户与非目标

### 目标用户

- 技术型个人用户（开发者、独立创作者、研究者），愿意自托管、自带模型 API key。
- 有明确的「重复性个人任务」：整理资料、盯盘/盯站、日报周报、文件归档、跨应用搬运信息。
- 在意数据边界：不希望把文件、邮件、聊天记录交给第三方 SaaS。

### 非目标（至少 12 个月内）

- ❌ 企业协作平台（多租户、SSO/SCIM、审计合规、按席位计费是另一个产品）。
- ❌ 通用 workflow builder / 低代码编排器。
- ❌ 面向非技术用户的消费级 App。
- ❌ 模型训练或推理基础设施。

> 注：**Bot 群聊（人 + 多个 bot 在同一会话里协作、互相 @）在范围内**，且优先级提前，见 §8 P1。它和多租户无关：群聊是「一个主人的多个助理同处一个线程」，不是企业账号体系。

## 4. 对标：Grok Bot 拆解

xAI 的 Grok Bot 是目前「个人 Agent 产品化」最完整的参照。它的能力可以拆成七块：

| # | 能力 | 本质 | 用户感知 |
|---|---|---|---|
| 1 | 创建/管理多个 Bot | Bot 实体 + 人格 + 工具白名单 | 「我有几个不同分工的助理」 |
| 2 | 私聊 / 群聊协作 | 渠道适配器 + 会话路由 | 「像给同事发消息一样」 |
| 3 | @bot on X | 社交渠道读写 + 轮询 | 「它在我的信息流里」 |
| 4 | 文件与结果 | 产物落盘 + 回传 | 「它交付了东西，不只是说了话」 |
| 5 | 操作电脑与应用 | 浏览器/桌面自动化 + 沙箱 | 「它替我把事做完了」 |
| 6 | Skills & Routines | 技能库 + 真调度 | 「它记得怎么做，还会自己开始」 |
| 7 | 审批 / 安全 / 隐私 | 风险分级 + 审计 | 「危险动作会先问我」 |

外加 **Bot 群聊**（多个 bot + 人同处一个会话）与移动端（客户端）。

**关键判断**：这七块里，真正构成「助理感」的是 **1（人格）、6（主动性）、2（随叫随到）、4（交付物）**。3 和 5 是传播点，不是留存点；移动端是规模化之后的事。

**群聊的判断（2026-10，优先级提前）**：群聊要提前，理由不是「像 Slack」，而是单 bot 对话里用户得反复切换上下文——查行情的、写文案的、做汇总的分处三个会话，用户自己当人肉总线。群聊让这几个分工不同的 bot 同处一个线程、互相 @、互相补位，体感从「我有一个工具」变成「我有一支团队」。它是 **2（随叫随到）** 的一种形态，而不是多租户。

## 5. 我们的差异点

不做「Grok Bot 的克隆」，做它不做的那一半：

| 维度 | Grok Bot | 我们 |
|---|---|---|
| 部署 | 托管在 xAI | **自托管在你的机器/服务器** |
| 数据 | 经过第三方 | **文件、密钥、对话不出门** |
| 模型 | 绑定 Grok | **BYO model**（DeepSeek / OpenAI / Claude / 本地） |
| 能力边界 | 平台给的 | **你的文件系统、你的桌面、你的脚本** |
| 扩展 | 官方技能 | **SKILL.md + MCP，任意接** |

一句话：**Grok Bot 住在 X 上，小巧住在你的机器上。**

## 6. 能力现状盘点

「有」和「是壳」必须分清，否则路线图会自欺。

### 6.1 已具备（可直接复用）

| 能力 | 位置 | 说明 |
|---|---|---|
| Agent 执行循环 | `agent_runtime.py`、`turn_runner.py` | `create_harness_agent` + 事件翻译，细粒度事件 |
| HITL 审批 | `agent_runtime.py`（`resolve_approval`） | 原生审批暂停/恢复；当前挂在 gateway 内存 |
| 事件协议 | `events.py`、`gateway/ws_server.py` | 前端已消费的稳定契约 |
| 工具集 | `tools/coding_tools.py` | shell、文件、搜索、HTTP、剪贴板、通知、todo |
| Skills | `skills.py` | SKILL.md 扫描/加载/安装 |
| MCP 连接器 | `mcp.py` | 安装、启停、工具注入 |
| Web UI | `web/` | Vue 3 + Pinia + UnoCSS，聊天/设置/自动化页面 |

### 6.2 是壳（本轮必须补）

| 缺口 | 证据 | 产品后果 |
|---|---|---|
| 定时任务不执行 | `automation.py` 仅 CRUD；全仓库无调度器；`run_count` 从不递增 | 「routines」卖点不成立 |
| 事件监听不触发 | 同上，`http/file_change/im_message` 只是字段 | 「自动化」页是摆设 |
| 人格不进模型 | 设置页只写 `localStorage`；Python 侧无 `SOUL` / personality 读取 | 改人格对回答零影响 |
| 系统提示词写死 | `system_prompt.py` 的 `_DEFAULT_INSTRUCTIONS` 是编码助手 | 产品气质不对 |
| 记忆/渠道/安全 | 三个页面均 369 字节占位 | 三个核心页面空白 |
| 单助手单会话 | `ws_server` 的 `self._session` 兜底；settings 全局单例 | 多 Bot 无从谈起 |
| 无群聊 | 无 Group 实体，会话只属于单 Bot | 「几个助理同处一个线程」无从谈起 |
| 无沙箱 | `_run_command` 直接在宿主执行 | 接渠道 = 远程命令执行 |
| 无鉴权 | WS 端口裸奔 | 无法公网部署 |

### 6.3 结构性隐患

- **MAF 私有 API**：`agent_runtime.py`、`turn_runner.py`、`settings.py` 等直接 import `agent_framework._types`、`_middleware`、`_clients`、`_skills`、`_tools`。下划线 = 非公开契约，框架升级必断。需要在 `llm/maf_adapter.py` 收口（见 pivot-plan §5）。
- **Python 3.14 下限**：托管环境支持面窄，部署时要么自带镜像，要么降版本。
- **无 CI**：测试靠手动，重构期风险放大。

## 7. 产品模型

### 7.1 核心概念

```
User（使用主体：你）                            ← 单用户，自托管
 ├── Bot（人格 + 模型 + 工具白名单 + 工作目录）
 └── Group（群聊：参与者 = 你 + N 个 Bot）       ← 协作场
      ├── Channel（Telegram / Web / X DM / 邮件）   ← 入口
      ├── Thread（某个外部会话）                    ← 路由到 Session
      ├── Session（Bot × 人 × 线程）                ← 每个 Bot 自己的上下文
      ├── Route（消息 → 收件人 Bot 的确定性规则）    ← @mention 路由
      ├── Routine（定时/事件触发的任务）             ← 主动性
      ├── Memory（facts + 会话摘要）                ← 长期记忆
      └── Artifact（产出物）                        ← 交付
```

- **Bot 是一等实体**。一个人可以有三个 bot：Coder、生活助理、盯盘员。
- **Group 也是一等实体**：参与者是「人 + 若干 Bot」，消息带作者与 `@mentions`；群有默认应答 Bot，也可以显式 `@` 某个 Bot 或 `@all`。
- **Session 属于 Bot × 人 × 线程**：同一个群里，每个 Bot 各自维护自己的上下文（工具调用配对不能混），但读的是同一份群消息流，带作者前缀。
- **Route 是确定性规则，不是编排**：一条用户消息解析出「谁该回」，Bot 的回复里再 @ 别的 Bot 才产生下一跳；有跳数上限与防环。
- **Routine 属于 Bot**，触发后产生一次 Run，结果回到指定群/渠道。
- **Memory 按 Bot × 人 隔离**，群聊里各 Bot 的长期记忆不串味。
- **Artifact 属于 Bot / Run**，群内可见；写工作区仍要过审批。

### 7.2 一次 Run 的生命周期

```
触发（渠道消息 / routine / 网页 / API）
   → 组装 prompt（基础契约 + 人格 + 记忆 + 渠道上下文 + 技能）
   → 执行（工具调用；高风险工具挂起等审批）
   → 产出（文本 / 文件 / 通知）
   → 回传（原渠道 + 网页事件流）
   → 沉淀（会话摘要 → 记忆；新文件 → 产物）
```

### 7.3 主动性分级

| 级别 | 行为 | 默认 |
|---|---|---|
| L0 被动 | 只在被叫到时响应 | — |
| L1 提醒 | 到点发消息 | ✅ 默认 |
| L2 代办 | 到点自己执行并交付结果 | 用户逐条开启 |
| L3 自主 | 发现事件（文件变化/网页更新）自行决定是否行动 | 实验性，需白名单 |

审批策略与主动性挂钩：L2/L3 的高风险工具（写文件、执行命令、对外发送）必须走审批，且审批要能在**收到消息的那个渠道里**完成。

## 8. 路线图

顺序不可交换：**先地基，再群聊与主动性，再渠道，再记忆，最后才碰电脑。**

> 为什么群聊在渠道之前：群聊是纯本地的协作模型（实体、路由、防环、UI），不依赖任何外部平台；而渠道（Telegram 群）只是把同一套 Group 模型映射出去。先把模型跑通，渠道接入才不用返工。

### P0 · 地基（约 1.5 周）

把「单助手」改成「多 Bot + 常驻运行时」。

- Bot 实体与 CRUD；`bot_id` 贯穿 session / routine / memory / channel。
- Gateway 瘦身为协议层，执行下沉到 Runtime；所有请求带 `botId`。
- SQLite 取代散落的 JSON；JSONL 降级为导出格式。
- 人格真正进入 system prompt；编码规范降级为「Coder」模板。

**验收**：建两个 bot（Coder / 生活助理），人格、模型不同，会话不串；切换 bot 后 prompt 实际变化；关掉网页，进程仍在。

### P1 · 群聊 + 主动性（约 2 周）

- Group 实体：名称、成员（你 + N 个 Bot）、默认应答 Bot；创建/编辑/归档。
- `@mention` 路由：`@bot` 指定回复、`@all` 全员、无 mention 走默认 Bot；Bot 回复里 @ 别的 Bot 触发下一跳。
- 防环与预算：每个用户消息最多 3 跳、每轮最多 3 个 Bot、同一 Bot 不得连续自触发；超限即停并提示。
- 群内上下文：每个 Bot 维护自己的 Session（工具配对不混），读同一份群消息流并带作者前缀。
- 群内审批：只有人类能点；Bot 之间不能互批。
- 调度器：20s tick、`routine_fires` 去重、启动补偿；routine 结果投递到指定群。

**验收**：建群（Coder / 盯盘 / 生活助理）；`@盯盘 查一下今天的行情`，它回帖后 `@Coder 整理成日报`，Coder 接棒产出；连续互 @ 到 3 跳自动停；9:00 日报主动发到群里；Bot 点审批被拒。

### P2 · 渠道（约 1 周）

- Telegram 适配器：私聊与群组；群组映射到内部 Group，`@bot` 与 Bot 账号名对齐。
- 审批持久化：跨渠道、TTL 自动拒绝；群内按钮只在人类点击时生效。
- 消息归属：Bot 发出的消息带 Bot 身份，人类消息带用户身份，避免「谁说的」混淆。

**验收**：Telegram 群里多 Bot 互相 @ 能跑通；能收文件、点按钮审批；每天 9:00 日报能发到 Telegram 群。

### P3 · 记忆 + 交付（约 1.5 周）

- facts 注入 + 会话结束摘要 + 关键词检索（FTS5 起步）；群聊摘要按 Bot 分别沉淀。
- 产物索引：run 结束扫描工作区新文件，网页可预览、渠道可发送。
- 提示注入防护：渠道输入标记 untrusted；高风险工具强制审批。

**验收**：新会话里记得上周的偏好；群聊里 Coder 能接上盯盘员上一轮的结论；产出的 md/xlsx 能预览并发送。

### P4 · 规模化（按需）

- Playwright 工具 + Docker 沙箱执行器。
- 每 Bot / 每群预算与速率限制（群聊一次消息可能触发多个 Bot，成本要可见）。
- X DM、移动端；多租户（多人账号体系）仍为远期评估项，不与群聊混为一谈。

## 9. 关键决策

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | Bot 作为一等实体，而非「用户」 | 产品叙事是「我有几个助理」；也是多 bot 隔离的天然边界 | 所有表加 `bot_id`，一次性迁移 |
| D2 | 执行下沉到 Runtime，Gateway 降级为客户端 | routine/渠道不能依赖浏览器在线 | 需要重写 `ws_server` 的调用路径 |
| D3 | 单 Bot 单 Agent，不上多 agent 任务编排；群聊是消息路由，不是编排 | 个人场景一个 agent 足够；编排只增加调试成本；群聊里每个 Bot 独立跑自己的 Agent | 跨 Bot 的复杂任务靠互相 @ 与交接，不靠中心调度器 |
| D4 | SQLite 起步，不上 Postgres/Redis | 单用户、单机；换库成本低于运维成本 | 多用户/多机时需迁移 |
| D5 | 渠道先 Telegram，X DM 最后 | Telegram 免费、支持文件、inline keyboard 天然适合审批；X 有审核/限流/封号风险 | 失去 X 生态传播 |
| D6 | 沙箱接口先留，实现后置 | 本地单用户可接受宿主执行 + 审批；接口留好避免返工 | 公网部署前必须补 |
| D7 | 发行名迁到 `xiaoqiao`，保留 `coding-agent` 别名 | 品牌与包名一致；PyPI `xiaoqiao` 可用；旧目录自动兼容，迁移零操作 | 需一次性改 pyproject / 构建脚本 / 文档；CI 或脚本中写死 `coding-agent` 的需更新 |
| D8 | Group 是一等实体（人 + 多 Bot），Session 仍按 Bot 隔离 | 群里每个 Bot 的工具调用配对不能混在一份上下文里；共享的是消息流，不是会话状态 | 群内上下文要按 Bot 组装并裁剪；存储上多一层 group→session 映射 |
| D9 | 群聊路由是确定性规则，不是多 agent 编排 | 可预测、可测试、可解释；编排器会把调试成本翻倍 | 复杂的「多角色协同」只能靠 @ 交接，不能自动分工 |
| D10 | 防环是硬约束：每用户消息最多 3 跳、每轮最多 3 个 Bot、同 Bot 禁止连续自触发 | Bot 互 @ 很容易变成无限对话与账单事故 | 部分合理的长链路需要用户手动再 @ 一次 |
| D11 | 群内审批只有人类可批，Bot 之间不能互批 | 否则「审批」退化为 Bot 之间的礼貌确认 | 人在离线时 run 会停在 waiting_approval，需 TTL |

## 10. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| MAF 私有 API 变更 | 升级即断 | 适配层 + 锁版本 + 契约测试 |
| 审批绑死在 WebSocket | routine/渠道触发的任务永久挂起 | 审批落库 + 渠道按钮 + TTL |
| 渠道输入提示注入 | 诱导 agent 执行危险操作 | untrusted 标记 + 工具白名单 + 强制审批 |
| 成本失控 | routine 高频 + 大上下文 | 每 bot 日预算、routine 用便宜模型、`max_turns` 上限 |
| 单点常驻进程 | 崩溃后 routine 全停 | 进程守护 + 启动补偿（补跑错过的任务） |
| **Bot 互 @ 死循环** | 无限对话、token 账单爆炸 | 跳数/轮次/冷却三重上限；命中即停并在群里提示 |
| **群聊上下文膨胀** | 每个 Bot 都要读全量群消息 | 按 token 预算裁剪；近期消息全量、早期只留摘要；单条消息超长截断 |
| **多 Bot 回复乱序** | 同一时刻多个 Bot 回帖，顺序不可读 | 群级发送队列串行化；每条回复带 reply-to，前端按序渲染 |
| **审批在群里被淹没** | 没人点，run 挂到 TTL | 审批卡片置顶 + 未批提醒；`/approvals` 收件箱兜底 |
| 范围蔓延 | 同时做渠道、沙箱、记忆、群聊 | 严格按 P0→P4；上一阶段未验收不碰下一阶段 |

## 11. 成功指标

不做 DAU 自欺。个人 Agent 的指标应该是「它替你干了多少活」：

- **北极星**：每周由 bot 主动完成、且被用户接受（未撤销/未重做）的任务数。
- **激活**：建 bot → 接一个渠道 → 跑通一条 routine，三步完成率。
- **留存**：第 4 周仍有至少一条 enabled routine 的用户比例。
- **信任**：审批通过率（过低=太保守，过高=审批形同虚设）、危险工具误触率。
- **群聊采纳**：至少含 2 个 Bot 的群占比、群内 `@` 触发的有效响应率、每群每周的 Bot 交接次数（群聊提前后的核心验证指标）。
